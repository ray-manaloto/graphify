# Codex, Git worktrees, mise, and hk: primary-source review

Research date: 2026-09-29. Scope: worktree behavior relevant to Graphify, knowledge-base, dotfiles, and their Codex chats. This is a research note, not a claim that any delivery gate passed or that ownership transferred.

## Findings

1. **Keep each writing chat in its own checkout.** Codex-managed worktrees normally start from the selected branch's `HEAD` in a detached state under `$CODEX_HOME/worktrees`. A user-created local worktree may instead have its own branch. A branch cannot normally be checked out simultaneously in another worktree. These are distinct facts: a path is a checkout, a branch is a ref, and neither implies remote publication. Git shares repository metadata and refs, while each worktree has its own `HEAD` and index. Check the actual path, branch/detached state, head, and `git worktree list --porcelain -z` before acting. [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees); [Git worktree](https://git-scm.com/docs/git-worktree).

2. **Use Codex Handoff for an app-managed chat move, and settle a writer before starting another.** OpenAI says Handoff handles the Git operations needed to move a chat between Local and Worktree. Parallel goals have independent contexts and goals, but should not modify the same files. A new checkout separates file/index state; it does not itself grant write ownership over a shared delivery branch, remote PR, evidence index, or goal. That last sentence is an inference from Git's shared refs and OpenAI's parallel-goal guidance, and should be enforced by the project's single-writer protocol. [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees); [Long-running work](https://learn.chatgpt.com/docs/long-running-work#run-goals-in-parallel); [Git worktree](https://git-scm.com/docs/git-worktree).

3. **Preserve ignored setup inputs deliberately.** Local Codex-managed worktrees contain tracked files. `.worktreeinclude` at the repository root can copy selected ignored local files into *new local managed* worktrees; ignored `AGENTS.override.md` is copied automatically. Codex skips source symlinks and existing targets. The feature does not apply to remote or manually created Git worktrees. Treat any copied secret-bearing file as an explicit setup decision. Verify needed ignored inputs in the actual checkout rather than assuming they followed a Handoff. [Codex worktrees, advanced details](https://learn.chatgpt.com/docs/environments/git-worktrees).

4. **Archive completed scheduled runs and preserve active work.** Worktree-backed schedules can accumulate one checkout per run. OpenAI recommends archiving unneeded scheduled runs and avoiding pins unless their worktrees must remain. Codex-managed cleanup protects pinned, in-progress, and permanent worktrees, and saves a snapshot before deletion; it is still necessary to check what a run owns before archiving. A chat heartbeat returning to the same chat differs from a standalone scheduled task that creates a new chat each run. [Scheduled tasks](https://learn.chatgpt.com/docs/automations#worktree-cleanup-for-scheduled-tasks); [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

5. **Use Git's worktree-aware commands, not `.git` path assumptions.** `git worktree list --porcelain -z` is the stable machine-readable inventory. `git rev-parse --show-toplevel`, `--git-common-dir`, and `--git-path` resolve the actual checkout and Git metadata. The common repository config is shared by default; `extensions.worktreeConfig=true` permits per-worktree config written with `git config --worktree`, but enabling the extension requires reviewing existing shared `core.worktree`, `core.bare`, and sparse-checkout values. `git worktree remove` is the Git cleanup command for manual linked worktrees; `repair` fixes broken links after moves. For Codex-managed worktrees, prefer the app's managed archive/restore lifecycle rather than shell deletion. [Git worktree](https://git-scm.com/docs/git-worktree); [Codex worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees).

6. **Tie mise execution to the intended checkout.** `mise -C <checkout> run <task>` changes directory before loading/running the task. Mise normally runs file tasks from the `mise.toml` directory; tasks can use `MISE_PROJECT_ROOT`, `MISE_CONFIG_ROOT`, and `MISE_ORIGINAL_CWD` rather than a hard-coded default clone path. A task with `sources`/`outputs` may skip due to freshness; a skipped invocation is not proof of a fresh test. Read the task's actual output and exit code. [mise CLI](https://mise.jdx.dev/cli/); [mise tasks](https://mise.jdx.dev/tasks/); [mise file tasks](https://mise.jdx.dev/tasks/file-tasks.html); [mise run](https://mise.jdx.dev/cli/run.html).

7. **Check mise trust at the worktree boundary.** In normal mode, mise shares trust for equivalent config paths between a main checkout and linked worktrees. Paranoid mode disables that sharing because different branches can contain different config contents. `mise trust --show` inspects status without changing it. This sharing means “trusted” does not prove the checked-out task content is identical to the main checkout; review the exact config/ref before running powerful tasks. [mise trust](https://mise.jdx.dev/cli/trust.html).

8. **Use one hk installation scope and verify actual execution.** With Git 2.54+, hk recommends `hk install --global --mise`; it registers hooks in the user's Git config and prepares each project's environment with `mise x`. A normal repo-scoped `hk install` skips if global hk hooks are present; forcing both scopes can double-run hooks. On older Git, repo-scoped install falls back to shims. Git runs non-bare hooks from the worktree root, but hook processes inherit Git environment variables; clear them before operating on a different worktree/repository. Inspect `git config --show-origin --get-regexp '^hook\.hk-'` and `git config --show-origin --get core.hooksPath`, then use `hk run pre-commit --plan` or `hk check --all --plan --json` to inspect selection. Plans do not execute linter steps; a real hook result requires its direct run/exit evidence. [hk install](https://hk.jdx.dev/cli/install.html); [hk mise integration](https://hk.jdx.dev/mise_integration); [hk troubleshooting](https://hk.jdx.dev/logging); [Git hooks](https://git-scm.com/docs/githooks).

9. **Treat `hk check` as a configured command, not an immutable read-only guarantee.** hk's docs state a check command conventionally reports problems but hk does not enforce immutability. A pre-commit fixer may edit and stage files, and stashing may isolate staged content. Inspect the hook plan and configuration before invoking checks in a checkout another writer owns. [hk configuration](https://hk.jdx.dev/configuration); [hk troubleshooting](https://hk.jdx.dev/logging).

10. **Keep nested worktrees and services distinct.** For a mise monorepo root, a linked checkout placed *inside* the main checkout still inherits ancestor tools, environment, and vars, even though its task namespace uses the nearer monorepo root. Keeping worktrees outside the main checkout avoids that unintended inheritance. If mise daemons are used, its default worktree namespace isolation gives linked worktrees separate service IDs, data, and automatic ports; a literal fixed connection URI is not rewritten. No daemon configuration change follows without an actual daemon use case. [mise monorepo tasks](https://mise.jdx.dev/tasks/monorepo.html); [mise development stack](https://mise.jdx.dev/daemons/development-stack.html).

11. **Distinguish Codex project hooks from hk Git hooks.** A merged upstream Codex change makes linked worktrees use project-hook declarations from the root checkout's matching `.codex/` folder, while ordinary project configuration can still come from the linked checkout. The source adds a regression test showing the same hook key, root source path, and trust state for both. This does not prove a given desktop build loaded that behavior or that any hook executed in this user's chat; inspect `hooks/list` and direct runtime traces for those claims. It also does not change Git's separate hk pre-commit/commit-msg/pre-push registration. [OpenAI Codex commit 934a40c](https://github.com/openai/codex/commit/934a40c7d9606a79bce472560fa665705293162f); [Git hooks](https://git-scm.com/docs/githooks).

## Local read-only observations

- `git --version`: `2.54.0 (Apple Git-157)`; `mise --version`: `2026.9.16 macos-arm64`; `hk --version`: `2.4.0`.
- In the Graphify, knowledge-base, and dotfiles main checkouts, `git config --show-origin --get-regexp '^hook\.hk-|^core\.hooksPath$|^extensions\.worktreeConfig$'` showed `hook.hk-pre-commit`, `hook.hk-commit-msg`, and `hook.hk-pre-push` from `~/.gitconfig`, each launching hk through `~/.local/bin/mise x hk`. No `core.hooksPath` value appeared. Graphify and dotfiles have `extensions.worktreeConfig=true` in their common repository configs; knowledge-base did not report that extension. This confirms installed configuration, **not** a particular hook firing or passing. Current global hk installation matches the official recommended Git 2.54+ route; adding a forced local installation would risk duplicate execution.
- In the isolated Graphify research checkout, plain `hk run pre-commit --plan` returned rc 1 (`Hook 'pre-commit' not found`) because this repository has no hk project hook definition. The exact global Git-hook route, `mise x hk -- hk run pre-commit --from-hook --staged --plan`, returned rc 0 with no selected steps, and its actual `--from-hook --staged` invocation also returned rc 0 with no output. Thus a global hook registration can correctly be a no-op for a repo without an hk hook, while a plain plan command has different behavior. Neither no-op validates code or documentation.

## Recommended application and evidence gaps

- Keep the existing sole writer in the knowledge-base integration worktree.
